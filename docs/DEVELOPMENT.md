# Development

Notes for building InstaFind (crate `bahth`) and finding your way around the code. Users only need the [README](../README.md).

## Build

On Windows, with Rust from <https://rustup.rs> (and the Visual Studio C++ Build Tools when rustup asks):

```
cargo build --release      # target\release\bahth.exe
cargo run --release
cargo test                 # the search, index and extraction tests also run on Linux
```

The published exes are built on Windows with MSVC and a static C runtime (`+crt-static` in [`.cargo/config.toml`](../.cargo/config.toml)), exactly as the `exe` and `exe-arm64` jobs do, so they run without the Visual C++ Redistributable:

```
rustup target add x86_64-pc-windows-msvc i686-pc-windows-msvc aarch64-pc-windows-msvc
cargo build --release --target x86_64-pc-windows-msvc    # bahth.exe (x64)
cargo build --release --target i686-pc-windows-msvc      # bahth-x86.exe (32-bit)
cargo build --release --target aarch64-pc-windows-msvc   # bahth-arm64.exe (ARM64)
python ci/check_imports.py bahth.exe                     # no VCRUNTIME / non-system DLL imports, DLLs from System32 only
```

From Linux, a mingw cross-build still works for a quick local check (`rustup target add x86_64-pc-windows-gnu`, `sudo apt-get install mingw-w64`, `cargo build --release --target x86_64-pc-windows-gnu`), but nothing published is built that way.

## Checks

Every push and pull request runs [`.github/workflows/build.yml`](../.github/workflows/build.yml): `cargo clippy --all-targets -D warnings` on Linux and Windows, `cargo test` (debug and release) on Linux and `cargo test --release` on Windows, then the MSVC builds (static CRT) of `bahth.exe` (x64) and `bahth-x86.exe` (32-bit) on Windows, a native build and `cargo test --release` of `bahth-arm64.exe` on a `windows-11-arm` runner (MSVC, static CRT), an import check of each exe ([`ci/check_imports.py`](../ci/check_imports.py): no Visual C++ runtime, no DLL outside Windows, and `DependentLoadFlags` 0x800 so Windows takes the imported DLLs from System32 and not from the exe's folder, ASLR/DEP/high-entropy ASLR and Control Flow Guard in the PE header; `--mingw-ok` for a local mingw build), and a smoke test of each exact exe on real Windows of its CPU (x86 under WOW64) ([`ci/smoke.ps1`](../ci/smoke.ps1)): the GUI indexes the runner's drives, the command line searches the index (Arabic, emoji, long names, filters), and any `crash.txt` or early exit fails the job. Two more jobs check the supply chain: `deny` runs [cargo-deny](https://embarkstudios.github.io/cargo-deny/) with [`deny.toml`](../deny.toml) (RustSec advisories, licences, sources, for the Windows targets), and `zizmor` audits the workflows ([`.github/zizmor.yml`](../.github/zizmor.yml)). Every `uses:` is pinned to a full commit SHA, and the jobs that build the published exes use no build cache.

The `ui` job ([`ci/ui-test.ps1`](../ci/ui-test.ps1)) then uses the x64 exe like a person on a real Windows desktop. It types with real keystrokes and clicks with the mouse. It covers the first-run question, the floating box, Arabic and English searches (no hamza, wrong keyboard layout, Arabizi, typos), search inside documents, the right-click and Options menus, the Ctrl+Alt+F popup (apps by Arabic name, answers, Settings pages), the Arabic interface, the close button and Alt+F4 hiding to the tray, repeated clicks on the floating box, the indexing progress in the status bar, and a copy run from Downloads moving itself to `%LOCALAPPDATA%\Programs\InstaFind` (probes). **Core** checks fail the job. **Probe** checks report missing features (`MISS`) without failing it. The table goes to the job summary, and a screenshot of every step goes to the `ui-test` artifact. The popup draws its own rows, so when `BAHTH_UI_TEST` is set it writes them to `quick-rows.txt` (and its indexing progress line to `quick-note.txt`) for the test to read. With `BAHTH_TEST_SAVE_DELAY_MS=<ms>` set (read once at start, at most 600000, inert when unset or not a number) every index save waits that long before it writes, so a memory test can make saves slower than the file changes; `log.txt` then starts with `test hook: BAHTH_TEST_SAVE_DELAY_MS set; every index save waits <ms> ms`. The `release` job waits for `ui` as well as the build, test and smoke jobs.

## Releases

Only on InstaFind's train day (Saturday, once the owner says «موافق»), in one pull request; the checklist and the rollback steps are in [ROADMAP.md](../ROADMAP.md) ("Release checklist + rollback").

1. Bump `version` in `Cargo.toml`, and turn CHANGELOG.md's «غير منشور (Unreleased)» heading into `## X.Y.Z — <date>` ([CHANGELOG.md](../CHANGELOG.md); remove its `<!-- pending: ... -->` comments).
2. Write `releases/vX.Y.Z-notes.md`. The first line, `# title`, becomes the release title; then the Arabic body, then a short **English:** line. The `release` job passes the whole file as the body (the `# title` line included, as for every earlier release); a later edit of the file re-syncs the body without it. Remove or resolve every `<!-- pending: ... -->` comment first: GitHub hides HTML comments when it shows the release, but they stay in its text.
3. Update the version on the site: `softwareVersion`, the version lines and the download button in `site/index.html` and `site/en/index.html` (`pages.yml` publishes them on merge).
4. Merge to `main`. When the version has no tag yet and every job it needs passed (`linux-test`, `windows`, `smoke`, `ui`, `newlook`), the `release` job publishes the very `bahth.exe`, `bahth-x86.exe` and `bahth-arm64.exe` the smoke tests ran, plus `SHA256SUMS.txt`, creates the tag, marks the GitHub Release as *latest*, and starts `packaging.yml` and `store.yml` with the new tag.

Signed updates ([docs/specs/signing.md](specs/signing.md), owner steps in Arabic there): releasing is `version` → `sign` → `release`, and `version` waits for every check (`linux-test`, `windows`, `smoke`, `ui`, `newlook`). `sign` runs in the Environment `release` (secrets `MINISIGN_SECRET_KEY`, `MINISIGN_PASSWORD`), signs the three exes with minisign (trusted comment `instafind <tag>`) and checks them against `keys/*.pub`; `release` publishes the exes, their `<exe>.minisig` files and `SHA256SUMS.txt` (which then lists the `.minisig` files too) through a draft of its own commit whose target and assets (names and SHA-256) are checked before it is published as *latest*; the three jobs have concurrency groups, so two release runs never overlap. Until the owner has run `keys/ceremony.sh` and added the secrets, `sign` passes with a warning and releases go out exactly as before (three exes + `SHA256SUMS.txt`), and the app (`update::TRUSTED_PUBLIC_KEYS` empty) checks the SHA-256 only and logs `signature checking not configured`. Committed `keys/*.pub` without the secret fail `sign`. Once keys are compiled in, a missing or bad signature is refused. With "Required reviewers" set on the Environment, every release waits for the owner's **Review deployments → Approve** on the `sign` job (an unanswered approval expires after 30 days; push again or re-run then). Never rename `keys/` or `keys/ceremony.sh`, and keep `keys/*.pub` and `TRUSTED_PUBLIC_KEYS` in step (`update::tests::keys_dir_matches_trusted_keys`).

The in-app updater (`src/update.rs`) reads the latest release and downloads the asset for its own CPU: exactly **`bahth.exe`** on x64 (every installed copy since 0.3.0 looks for that name, so never rename it), `bahth-x86.exe` on 32-bit and `bahth-arm64.exe` on ARM64 (`ASSET_NAME`). Keep those names, keep releases out of draft/prerelease, and keep the repository URL. The job also attaches `SHA256SUMS.txt` (`sha256sum` of the three exes) as a fourth asset, the official checksums file from 1.0 on. <!-- pending: signed updates (R8): with the signing keys, one `<exe>.minisig` per exe as well (claude/instafind-1.0-signing, docs/specs/signing.md). --> Editing a `releases/*-notes.md` file later re-syncs that release's title and body ([`release-notes.yml`](../.github/workflows/release-notes.yml)); assets are never touched.

The updater fails closed: it installs a release only when GitHub publishes a SHA-256 `digest` for the asset (it does for every upload), and refuses it otherwise, pointing to the manual download. When the GitHub API is rate-limited, a release found through the web page still needs the API for its digest; while the API refuses, the check counts as failed and is retried an hour later, and a manual check says «تعذّر التحقق الآن، سنحاول لاحقاً.» / "Could not verify the update right now; we will try again later." (`with_digest`). A copy installed with Scoop (under `%SCOOP%`/`%USERPROFILE%\scoop` `apps\` or `shims\`), winget (under `...\WinGet\Packages\` or `Links\`) or Chocolatey (`lib\` or `bin\` under `%ChocolateyInstall%` or `%ProgramData%\chocolatey`), and a Microsoft Store copy (`store::is_packaged`), never updates itself: the manual check says to run `scoop update instafind` / `winget upgrade Sarmad.InstaFind` / `choco upgrade instafind`, or offers the Store page (`update::package_manager_for`, `update::managed_by`). A copy in a folder it cannot write to (Program Files) is offered no update either; the manual check says to download from fastkiwi.app or move the program to a folder of the user's own.

Installing an update hands over to the new copy (`src/handover.rs`, tested on Linux; `src/leave.rs` for the exit deadlines): the old copy starts it with `--prev-pid=<id>:<creation time>` and watches it for 3 s; if it ends at once `bahth.exe.old` is put back. The new copy waits at most 10 s for the old one, ends it if needed, and deletes `bahth.exe.old` / `.new` only after its first timer tick. `update-trial.txt` (written at an `--updated` start, removed at the first tick) makes the next start roll back a version that never finished starting. A move and a language change use the same handover. A newer copy started while an older one runs (or while an older one is installed and this one runs from Downloads or a temp folder) replaces it with no question (`src/ui/older_copy.rs`, decisions in `handover::second_start`): it asks the running copy for its version (registered message `BahthSari.Identify.v1`; a copy before 1.0 is read from its exe's version resource and `QueryFullProcessImageNameW`), puts itself in place of the old exe with the updater's swap (`bahth.exe.old` kept for the trial), asks the old copy to leave (`BahthSari.LeaveForNewerCopy.v1`, or WM_CLOSE / an immediate end for 0.10.0), and starts the program from the old place with `--updated --replaced=<old> [--remove-download=<path>]`. Program Files, package-manager and Downloads/temp copies keep their file (the old copy is closed and the new one runs where it is); an older or the same version, and a Store copy against a portable one, only bring the running copy to the front.

## Known gaps

**The look.** Since 1.0 the new look (`src/ui/webui.rs`) is the only look where it can run (an MSVC build, which every published exe is, and the WebView2 runtime); there is no way back to the classic window. `Settings::make_new_look_only` turns `new_ui` on for good at every start; the first time (marker `new_ui_only`) it moves users who chose the classic window, whether they came from 0.10.0 or from a 1.0 test build that wrote `new_ui_default` (that key is still written, because `i18n.rs` reads it as "written by a version that has English"). **Fallback:** without WebView2, or when it fails to start (two tries) or its page fails twice, the classic ("simple") window takes over for that run only, with «يعمل البرنامج بالشكل البسيط لأن مكوّن WebView2 في ويندوز لا يعمل.» above its list; `new_ui` stays on, `new_ui_failed=1` (`Settings::note_fallback`) makes the next start try once and give up at the first failure (`webui::start_tolerance`), and a page that works a minute clears it. In that window, Options ▸ «جرّب الشكل الجديد» / "Try the new look" retries at once. **Test switches** (not for users): `--classic` or `BAHTH_CLASSIC=1` give the classic window without the line (the `ui` job), `BAHTH_WEBUI_FAIL=1` makes WebView2 count as failing (the fallback test), `--webui` or `BAHTH_WEBUI=1` force the new look for one launch. `BAHTH_WEBUI_RELEASE_SECS=20` shortens the time hidden before the page is released (the memory test). **Hidden:** hiding the window (to the tray) makes the page invisible to WebView2, asks for its low-memory level and suspends it (`TrySuspend`); after `webui::RELEASE_AFTER` (10 min) hidden without a break the WebView2 host is dropped so its processes exit, and the next show creates it again and sends the last search with its filters (`Outbound::Restore`). The decision is `webui::idle_action` (never during a Save/Open hand-off, under a modal, or while a search inside documents runs); a release is not a failure (`new_ui_trying`/`new_ui_failed` untouched, no fallback). Log lines: `webui: suspended (hidden)`, `webui: released after 10 min hidden`, `webui: recreated on show in N ms`.

- Thumbnail view (Ctrl+T): the new look has its own grid (toolbar button or Ctrl+T, kept in the page's storage); the classic Options item stays greyed out while the new look is in use. Thumbnails are the classic view's shell pictures made by `src/ui/webui_thumbs.rs` (two workers, newest first, a bounded queue, a 256-PNG LRU the memory guard drops) and served through `instafind://` as `/thumb/<key>`: the page asks for rows of a list version (`Request::Thumbs`) and gets random one-time keys, never paths; an unknown key or a file without a thumbnail is a 404. Not yet seen on real Windows: the asynchronous protocol answer from the worker threads, picture quality at 150 % and more.
- Column widths: every column of the new look's list can be dragged at the end of its header (or moved with the arrow keys on that edge; a double click resets it) and is kept in the page's storage, not in `settings.txt` as the classic columns.
- Ctrl+Alt+G (move a Save/Open dialog to a result's folder) works in both looks (`quickswitch::quick_switch_to`): in the page a line shows the hint while the dialog waits, Enter moves it, Esc cancels and the result menu has the move first. Not yet seen on real Windows.
- The quick popup's own owner-drawn result rows have no accessible names (its search box is named through `ui/accessible.rs`).
- The Options menu (tools, support, updates, Alt+Space, the floating box's modes) opens over the new window from Settings › More › "Open the Options menu…" or the tray's "Settings…" (`webui_options_menu`: owned by the new window, the chosen item passed to the classic window's handlers). Items that work on the main window act on the new look while it is in use: export (the page's results), duplicates (the page's results), folder sizes (the page's folder), hide to the tray; the thumbnail item is greyed out; status-bar messages (update download %, "Exported N results"…) show as the page's notice; switches refresh the page's settings.
- Dragging a result out (`Request::Drag`): the program drags the file only while the left button is still down over the window (else it logs "drag skipped").
- Screen readers and high contrast: ARIA roles, names and keyboard paths (the recent files, the column edges) and a `forced-colors` style exist, and `preview.cjs` checks that every visible control has a name; the CI test drives the page through UI Automation, but nobody has used it with Narrator/NVDA.

Other known limits:

- Idle memory: two minutes after the last activity, once the warm-up has ended, the process drops its rebuildable caches and compacts the heap (`mem_guard::idle_trim_due`, log line `memory: idle trim: …`); the index and its normalised names stay. Task Manager's InstaFind group also counts the msedgewebview2 processes once the new look has been shown.

CI: the `ui` job tests the classic window (`BAHTH_CLASSIC=1`); the `newlook` job ([`ci/newlook-test.ps1`](../ci/newlook-test.ps1), x64 exe on `windows-latest`, `release` waits for it) checks a new user (no settings) gets the new look, its page loads and is painted, classic users of 0.10.x and 0.10.0 are moved once and `new_ui=0` after that is ignored, neither the settings page nor the Options menu over the new look offers the classic look, `BAHTH_CLASSIC=1` gives the classic window with "Try the new look", and with `BAHTH_WEBUI_FAIL=1` the classic window takes over with its line while `new_ui=1` stays, so the next start opens the new look; with `BAHTH_WEBUI_RELEASE_SECS=20` a hidden window's msedgewebview2 processes exit, without a fallback or a failure marker, and a second launch creates the page again with the query kept; a plain click on a result selects it and starts no drag, and a real drag onto the page's own search box is a probe. Not exercised: the fallback after a WebView2 crash of a running page; the x86 and arm64 exes with the new look. Screenshots and diagnostics are in the `newlook-test` artifact.

## Testing on Wine

The exe runs under Wine for quick checks (`LANG=C.UTF-8`, otherwise Arabic paths fail). Wine draws list items mirrored under right-to-left layout, so check list rendering on real Windows.

## Microsoft Store

[`store.yml`](../.github/workflows/store.yml) packs the three exes into an unsigned `.msixbundle` (artifact `store-package`) from `packaging/msix/` (manifest template, `identity.json`, logos). It runs only for a published release (`build.yml`'s release job starts it with the new tag, because a release made with `GITHUB_TOKEN` fires no `release` event) or by hand (Actions ▸ store ▸ Run workflow, with a tag, or empty for a test build from the branch); there is no pull-request trigger. Every run installs a test-signed copy (`packaging/msix/test-install.ps1`) and captures the listing screenshots (`ci/store-shots.ps1`). <!-- pending: S1: the Store screenshots still show the classic window; retake them with the new look. --> The same exe detects that it runs packaged (`src/store.rs`): no self-update, start-with-Windows through the package's StartupTask, data redirected by Windows into the package's AppData. Submission steps, listing texts and certification notes: [docs/distribution/microsoft-store.md](distribution/microsoft-store.md).
