# Development

Notes for building InstaFind (crate `bahth`) and finding your way around the code. Users only need the [README](../README.md).

## Build

On Windows, with Rust from <https://rustup.rs> (and the Visual Studio C++ Build Tools when rustup asks):

```
cargo build --release      # target\release\bahth.exe
cargo run --release
cargo test                 # the search, index and extraction tests also run on Linux
```

The published exes are built on Windows with MSVC and a static C runtime (`+crt-static` in [`.cargo/config.toml`](../.cargo/config.toml)), exactly as the `exe` and `exe-arm64` jobs do, so they run without the Visual C++ Redistributable:

```
rustup target add x86_64-pc-windows-msvc i686-pc-windows-msvc aarch64-pc-windows-msvc
cargo build --release --target x86_64-pc-windows-msvc    # bahth.exe (x64)
cargo build --release --target i686-pc-windows-msvc      # bahth-x86.exe (32-bit)
cargo build --release --target aarch64-pc-windows-msvc   # bahth-arm64.exe (ARM64)
python ci/check_imports.py bahth.exe                     # no VCRUNTIME / non-system DLL imports, DLLs from System32 only
```

From Linux, a mingw cross-build still works for a quick local check (`rustup target add x86_64-pc-windows-gnu`, `sudo apt-get install mingw-w64`, `cargo build --release --target x86_64-pc-windows-gnu`), but nothing published is built that way.

## Checks

Every push and pull request runs [`.github/workflows/build.yml`](../.github/workflows/build.yml): `cargo clippy --all-targets -D warnings` on Linux and Windows, `cargo test` (debug and release) on Linux and `cargo test --release` on Windows, then the MSVC builds (static CRT) of `bahth.exe` (x64) and `bahth-x86.exe` (32-bit) on Windows, a native build and `cargo test --release` of `bahth-arm64.exe` on a `windows-11-arm` runner (MSVC, static CRT), an import check of each exe ([`ci/check_imports.py`](../ci/check_imports.py): no Visual C++ runtime, no DLL outside Windows, and `DependentLoadFlags` 0x800 so Windows takes the imported DLLs from System32 and not from the exe's folder, ASLR/DEP/high-entropy ASLR and Control Flow Guard in the PE header; `--mingw-ok` for a local mingw build), and a smoke test of each exact exe on real Windows of its CPU (x86 under WOW64) ([`ci/smoke.ps1`](../ci/smoke.ps1)): the GUI indexes the runner's drives, the command line searches the index (Arabic, emoji, long names, filters), and any `crash.txt` or early exit fails the job. Two more jobs check the supply chain: `deny` runs [cargo-deny](https://embarkstudios.github.io/cargo-deny/) with [`deny.toml`](../deny.toml) (RustSec advisories, licences, sources, for the Windows targets), and `zizmor` audits the workflows ([`.github/zizmor.yml`](../.github/zizmor.yml)). Every `uses:` is pinned to a full commit SHA, and the jobs that build the published exes use no build cache.

The `ui` job ([`ci/ui-test.ps1`](../ci/ui-test.ps1)) then uses the x64 exe like a person on a real Windows desktop. It types with real keystrokes and clicks with the mouse. It covers the first-run question, the floating box, Arabic and English searches (no hamza, wrong keyboard layout, Arabizi, typos), search inside documents, the right-click and Options menus, the Ctrl+Alt+F popup (apps by Arabic name, answers, Settings pages), the Arabic interface, the close button and Alt+F4 hiding to the tray, repeated clicks on the floating box, the indexing progress in the status bar, and a copy run from Downloads moving itself to `%LOCALAPPDATA%\Programs\InstaFind` (probes). **Core** checks fail the job. **Probe** checks report missing features (`MISS`) without failing it. The table goes to the job summary, and a screenshot of every step goes to the `ui-test` artifact. The popup draws its own rows, so when `BAHTH_UI_TEST` is set it writes them to `quick-rows.txt` (and its indexing progress line to `quick-note.txt`) for the test to read. With `BAHTH_TEST_SAVE_DELAY_MS=<ms>` set (read once at start, at most 600000, inert when unset or not a number) every index save waits that long before it writes, so a memory test can make saves slower than the file changes; `log.txt` then starts with `test hook: BAHTH_TEST_SAVE_DELAY_MS set; every index save waits <ms> ms`. The `release` job waits for `ui` as well as the build, test and smoke jobs.

## Releases

1. Bump `version` in `Cargo.toml` and add the entry to [CHANGELOG.md](../CHANGELOG.md).
2. Write `releases/vX.Y.Z-notes.md`. The first line, `# title`, becomes the release title; the rest is the release body (Arabic first, then a short **English:** line).
3. Push to `main`. When the version has no tag yet and the smoke test passed, the `release` job publishes the very `bahth.exe`, `bahth-x86.exe` and `bahth-arm64.exe` the smoke tests ran, creates the tag and marks the GitHub Release as *latest*.

The in-app updater (`src/update.rs`) reads the latest release and downloads the asset for its own CPU: exactly **`bahth.exe`** on x64 (every installed copy since 0.3.0 looks for that name, so never rename it), `bahth-x86.exe` on 32-bit and `bahth-arm64.exe` on ARM64 (`ASSET_NAME`). Keep those names, keep releases out of draft/prerelease, and keep the repository URL. The job also attaches `SHA256SUMS.txt` (`sha256sum` of the three exes, and of their `.minisig` files once releases are signed) as a fourth asset, the official checksums file from 1.0 on. Editing a `releases/*-notes.md` file later re-syncs that release's title and body ([`release-notes.yml`](../.github/workflows/release-notes.yml)); assets are never touched.

Signed updates ([docs/specs/signing.md](specs/signing.md), owner steps in Arabic there): releasing is `version` → `sign` → `release`, and `version` waits for every check (`linux-test`, `windows`, `smoke`, `ui`, `newlook`). `sign` runs in the Environment `release` (secrets `MINISIGN_SECRET_KEY`, `MINISIGN_PASSWORD`), signs the three exes with minisign (trusted comment `instafind <tag>`) and checks them against `keys/*.pub`; `release` publishes the exes, their `<exe>.minisig` files and `SHA256SUMS.txt` (which then lists the `.minisig` files too) through a draft whose asset list is checked before it is published as *latest*. Until the owner has run `keys/ceremony.sh` and added the secrets, `sign` passes with a warning and releases go out exactly as before (three exes + `SHA256SUMS.txt`), and the app (`update::TRUSTED_PUBLIC_KEYS` empty) checks the SHA-256 only and logs `signature checking not configured`. Committed `keys/*.pub` without the secret fail `sign`. Once keys are compiled in, a missing or bad signature is refused. With "Required reviewers" set on the Environment, every release waits for the owner's **Review deployments → Approve** on the `sign` job (an unanswered approval expires after 30 days; push again or re-run then). Never rename `keys/` or `keys/ceremony.sh`, and keep `keys/*.pub` and `TRUSTED_PUBLIC_KEYS` in step (`update::tests::keys_dir_matches_trusted_keys`).

The updater fails closed: it installs a release only when GitHub publishes a SHA-256 `digest` for the asset (it does for every upload), and refuses it otherwise, pointing to the manual download. A copy installed with Scoop (under `%SCOOP%`/`%USERPROFILE%\scoop` `apps\` or `shims\`) or winget (under `...\WinGet\Packages\` or `Links\`) never updates itself: the manual check says to run `scoop update instafind` / `winget upgrade Sarmad.InstaFind` (`update::package_manager_for`).

## Known gaps

The new look (`src/ui/webui.rs`) is the only look since 1.0 where it can run (MSVC build and the WebView2 runtime). `Settings::make_new_look_only` turns `new_ui` on for good at every start; the first time (marker `new_ui_only`, with 0.10.1's `new_ui_default`, which `i18n.rs` reads) it moves users who chose the classic window. Without WebView2, or when it fails to start (two tries) or its page fails twice, the classic window takes over for that run only, with «يعمل البرنامج بالشكل البسيط لأن مكوّن WebView2 في ويندوز لا يعمل.» above its list; `new_ui_failed=1` (`Settings::note_fallback`) makes the next start try once and give up at the first failure (`webui::start_tolerance`), and a page that works a minute clears it. What the classic main window has and the new look lacks or does differently (sizes: S small, M medium):

- Thumbnail view (Ctrl+T): the new look has its own grid (toolbar button or Ctrl+T, kept in the page's storage); the classic Options item stays greyed out while the new look is in use. Thumbnails are the classic view's shell pictures made by `src/ui/webui_thumbs.rs` (two workers, newest first, a bounded queue, a 256-PNG LRU the memory guard drops) and served through `instafind://` as `/thumb/<key>`: the page asks for rows of a list version (`Request::Thumbs`) and gets random one-time keys, never paths; an unknown key or a file without a thumbnail is a 404. Not yet seen on real Windows: the asynchronous protocol answer from the worker threads, picture quality at 150 % and more.
- Column widths: the new look's Size and Date columns can be dragged (the name column takes the rest); the classic window's every column.
- The Store rating row (Store copies) and its file-open count: classic only (S).
- The Options menu (tools, support, updates, Alt+Space, the floating box's modes) opens over the new window from Settings › More › "Open the Options menu…" or the tray's "Settings…" (`webui_options_menu`: owned by the new window, the chosen item passed to the classic window's handlers). Items that work on the main window act on the new look while it is in use: export (the page's results), duplicates (the page's results), folder sizes (the page's folder), hide to the tray; the thumbnail item is greyed out; status-bar messages (update download %, "Exported N results"…) show as the page's notice; switches refresh the page's settings.
- Dragging a result out (`Request::Drag`): the program drags the file only while the left button is still down over the window (else it logs "drag skipped").
- Screen readers and high contrast: ARIA roles and a `forced-colors` style exist; the CI test drives the page through UI Automation, but nobody has used it with Narrator/NVDA.

CI: the `ui` job tests the classic window (`BAHTH_CLASSIC=1`); the `newlook` job ([`ci/newlook-test.ps1`](../ci/newlook-test.ps1), x64 exe on `windows-latest`, `release` waits for it) checks a new user (no settings) gets the new look, its page loads and is painted, classic users of 0.10.x and 0.10.0 are moved once and `new_ui=0` after that is ignored, neither the settings page nor the Options menu over the new look offers the classic look, `BAHTH_CLASSIC=1` gives the classic window with "Try the new look", and with `BAHTH_WEBUI_FAIL=1` the classic window takes over with its line while `new_ui=1` stays, so the next start opens the new look; a plain click on a result selects it and starts no drag, and a real drag onto the page's own search box is a probe. Not exercised: the fallback after a WebView2 crash of a running page; the x86 and arm64 exes with the new look. Screenshots and diagnostics are in the `newlook-test` artifact.

## Testing on Wine

The exe runs under Wine for quick checks (`LANG=C.UTF-8`, otherwise Arabic paths fail). Wine draws list items mirrored under right-to-left layout, so check list rendering on real Windows.

## Microsoft Store

[`store.yml`](../.github/workflows/store.yml) packs the three exes into an unsigned `.msixbundle` (artifact `store-package`) from `packaging/msix/` (manifest template, `identity.json`, logos); `build.yml`'s release job starts it with the new tag. The same exe detects that it runs packaged (`src/store.rs`): no self-update, start-with-Windows through the package's StartupTask, data redirected by Windows into the package's AppData. Submission steps, listing texts and certification notes: [docs/distribution/microsoft-store.md](distribution/microsoft-store.md).
